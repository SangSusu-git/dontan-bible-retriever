# 성경 하이브리드 검색 API 설계

- **날짜**: 2026-08-02
- **브랜치**: `feature/hybrid-search`
- **상태**: 설계 승인됨, 구현 계획 작성 대기

## 1. 목적

성경 구절 검색을 기존의 "단순 텍스트 포함 매칭"에서 **의미 기반 검색까지 아우르는 하이브리드 검색**으로 확장한다. 사용자가 정확한 구절을 기억하는 경우와, 단어는 다르지만 의미가 비슷한 구절을 찾고 싶은 경우를 모두 지원한다.

외부에 배포되어 다른 서비스가 HTTP로 호출하는 검색 API 형태로 제공한다.

## 2. 핵심 요구사항

1. **정확한 문장 매칭**: 사용자가 구절 텍스트를 정확히(혹은 거의) 기억하지만 장·절 위치를 모를 때, 그 구절을 확실하게 최상단에 노출한다.
2. **정확한 단어 매칭(Sparse)**: 특정 단어가 들어간 구절을 빠짐없이 찾는다. 매칭되는 구절은 개수 제한 없이 모두 반환한다.
3. **의미 유사도 검색(Dense)**: 단어가 달라도 의미가 가까운 구절을 찾는다. 유사도 임계값 이상인 구절을 모두 반환한다(고정 top-k로 자르지 않는다).
4. 성경 특유의 고어체/경전체 어미(예: "-이니라", "-하시니라")를 다뤄도 검색 품질이 크게 떨어지지 않아야 한다.

## 3. 아키텍처: 3단 검색 구조

```
질의(query)
  │
  ├─ 1. Exact Match  ── 텍스트에 질의가 그대로 포함된 구절 (개수 제한 없음)
  │                     → 최상단에 "정확히 일치" 섹션으로 고정 노출
  │
  ├─ 2. BM25 (Sparse) ── 형태소 토큰 겹침, score > 0 인 구절 전부
  │                                                          ┐
  └─ 3. Dense (Semantic) ── 코사인 유사도 ≥ 임계값 인 구절 전부 ┘
                              │
                              └─ 2 + 3 을 RRF로 병합 → "관련 구절" 섹션으로 노출
```

**설계 원칙**: Exact Match는 확신도 100% 신호이므로 RRF 투표에 섞지 않고 별도 최상단 섹션으로 분리한다. BM25와 Dense만 RRF로 병합한다. 응답도 `exact_matches` / `related_matches` 두 섹션으로 나눠 UX를 명확히 한다.

### 3.1 Exact Match
- 질의 문자열이 구절 텍스트에 그대로 포함되는지 확인(공백·문장부호 정도만 정규화).
- 약 3만 절 규모라 별도 인덱스 없이 단순 순회로 수 ms 내 처리.
- 매칭된 구절 전부를 최상단에 노출.

### 3.2 BM25 (Sparse Retrieval)
- 라이브러리: `rank_bm25`(또는 더 빠른 `bm25s`) — 구현 시 확정.
- 토크나이저: **Kiwi(kiwipiepy)** 형태소 분석기. 한국어는 교착어라 공백 분리만으로는 recall이 크게 떨어지므로 형태소 분석 필수. Kiwi는 문어체 정확도가 높아(약 94%) 격식체인 성경 텍스트에 유리.
- **매칭되는 구절(score > 0)은 개수 제한 없이 모두 반환**. `argsort`로 무조건 top-k를 채워 score 0(비매칭) 구절이 섞이지 않도록 `score > 0` 필터링을 반드시 적용한다.
- (선택) "여호와", "하나님", "주" 같은 도메인 초고빈도 단어의 stopword 처리 여부는 구현·검증 단계에서 결정. BM25의 IDF가 이미 흔한 단어의 가중치를 낮추므로 필수는 아님.

### 3.3 Dense (Semantic Retrieval)
- 임베딩 모델: **`nlpai-lab/KURE-v1`** (MIT 라이선스).
  - BAAI/bge-m3를 한국어 query-document 쌍 200만 개로 파인튜닝. 한국어 검색 벤치마크에서 다국어 모델 대비 우수. 별도 query/passage prefix 불필요해 구현 단순.
  - 로컬에서 실행(무료·오프라인). sentence-transformers로 로드.
- 벡터 저장소: **ChromaDB**.
  - 3만 절 규모에서는 FAISS와 성능 차이가 거의 없고, 메타데이터 필터링(책/장/절/번역본)과 영속성이 내장되어 운영이 단순. 외부 배포 API 요구사항에 적합.
- **컷오프는 고정 top-k가 아니라 코사인 유사도 임계값 기반**. 임계값 이상인 구절을 모두 반환하므로, 관련 구절이 많으면 많이·적으면 적게 자연스럽게 나온다.
  - 임계값 후보 **0.8 vs 0.9를 실제 질의-정답 쌍으로 테스트해 경험적으로 결정**(3.5 검증 참조).

### 3.4 RRF (Reciprocal Rank Fusion)
- BM25 결과와 Dense 결과의 **합집합(union)** 에 대해 각 리스트에서의 순위만으로 `score = Σ 1/(k + rank)` 를 계산해 재정렬. (k는 관례상 60 전후, 구현 시 확정)
- RRF는 자체적으로 결과를 버리지 않는다. 두 리스트 길이가 달라도 정상 작동하며, 한쪽에만 있는 구절은 그쪽 기여분만 받는다.
- 점수 스케일이 다른 BM25/Dense를 가중합하는 것보다 순위 기반 RRF가 안정적이라 채택.

### 3.5 도메인 검증 (구현 초기 필수 단계)
KURE-v1·Kiwi가 성경 고어체에서 실제로 잘 동작하는지 검증된 자료가 없으므로, 본격 구축 전 짧은 검증을 수행한다:
- 현대어 질의 ↔ 고어체 정답 구절 쌍 20~30개를 만들어 recall/precision 측정.
- 같은 세트로 Dense 유사도 임계값 0.8 vs 0.9 튜닝.
- Kiwi로 성경 구절 몇 개를 토크나이징해 "-하시니라" 같은 어미가 붙어도 내용어 어간("창조" 등)이 깨지지 않는지 육안 확인.

## 4. 데이터

- **성경 텍스트 확보**: 공개된 텍스트 파일(개역개정 등)이 있는지 먼저 확인하고, 없으면 사용자가 아는 성경 API로 텍스트를 수집한다. (구현 1단계에서 확정)
- **인덱싱(오프라인, 1회성)**: 확보한 구절을 KURE-v1로 임베딩해 ChromaDB에 적재하고, 동시에 Kiwi 토큰화 결과로 BM25 인덱스를 구성한다. 각 구절은 책·장·절·번역본 메타데이터를 가진다.
- 데이터가 여러 번역본/주석으로 수십만 건 이상 커지면 그때 FAISS 등으로 전환 검토(현 단계에서는 불필요).

## 5. API

- **프레임워크**: FastAPI + uvicorn.
- **인증**: 간단한 API 키(고정 키를 헤더로 검증). 무단 사용 차단.
- **검색 엔드포인트(초안, 구현 시 확정)**:
  - 요청: `query`(문자열), 선택적 필터(book/translation 등), 선택적 Dense 임계값 override.
  - 응답: `exact_matches`(정확 일치 구절 배열) + `related_matches`(RRF 병합 구절 배열, 각 항목에 book/chapter/verse/text/score/source 표시).
- **최종 응답 상한선**: 기본적으로 관련 구절을 모두 반환하되, 극단적 상황(임계값이 너무 낮아 수천 건이 걸리는 경우) 방지를 위한 넉넉한 안전 상한(기본값 예: 500, 설정 가능)만 둔다. 상한은 결과를 의도적으로 제한하려는 게 아니라 응답 크기·속도 보호용.

## 6. 배포

- **Docker화**하여 외부 배포. 다른 서비스가 안정적으로 호출.
- 환경변수로 API 키·모델 경로·임계값 기본값 관리.
- 임베딩 모델과 인덱스 로딩 시간이 있으므로 **시작 시 1회 로드 후 메모리 상주**시켜 요청당 재로드를 피한다(시작 시간 최적화).

## 7. 컴포넌트 경계 (독립 단위)

- **Data ingest**: 성경 텍스트 확보·정규화 → 구조화된 구절 목록.
- **Indexer(오프라인)**: 구절 목록 → ChromaDB 임베딩 인덱스 + BM25 인덱스.
- **Retriever 3종**: ExactMatcher / BM25Retriever / DenseRetriever — 각각 질의를 받아 구절 리스트를 반환하는 동일 인터페이스.
- **Fusion**: BM25·Dense 리스트를 RRF로 병합.
- **API layer(FastAPI)**: 인증 → 3종 검색 호출 → Exact 최상단 + RRF 결과 조립 → 응답.

각 단위는 독립적으로 테스트 가능하도록 분리한다.

## 8. 명시적으로 범위에서 제외 (YAGNI)

- FAISS/대규모 벡터 DB 전환 (현 규모 불필요)
- 임베딩 점수·BM25 점수 가중합 튜닝 (RRF로 대체)
- 재랭킹(reranker) 모델, 다중 번역본 교차참조, 사용자 계정/권한 (초기 범위 밖)

## 9. 미결/구현 중 확정할 사항

- 성경 텍스트 소스(공개 파일 vs API) 및 번역본.
- BM25 라이브러리(`rank_bm25` vs `bm25s`)와 RRF의 k값.
- Dense 유사도 임계값(0.8 vs 0.9) — 검증으로 결정.
- 도메인 stopword 처리 여부.
- API 요청/응답 스키마 최종 형태.
